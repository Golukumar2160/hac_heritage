2. Deep Problem Statement Analysis

Root problem. MoSPI has rich transaction-level data (sanction, expenditure, progress, completion) but no scalable way to find which of ~100k works deserve a human's scarce verification time. The symptoms are cost overruns, delays, duplicates and suspected misuse.

Users.

Primary: MoSPI DIID monitoring officers, and District Authorities who can verify on the ground.
Secondary: State Nodal Authorities, MPs, and CAG/vigilance bodies as downstream consumers.

If unsolved. Audits stay retrospective, verification effort is spread randomly, and irregularities surface long after the money is spent.

What the PS explicitly asks for.

Analysis of sanctions, expenditures, cost estimates, progress, payments and asset creation.
Detection of cost overruns, duplicate works, delayed projects and deviations from norms.
Risk-based alerts, predictive insights and decision-support dashboards for four user tiers.
Automated compliance monitoring and early warning.

Success criteria (measurable).

Outcome	Metric
Better targeting	Precision@k of flagged works, verified by independent review
Low noise	False-positive rate per tier
Timeliness	Days from event to alert
Reduced manual effort	Works reviewed per confirmed issue, versus random sampling
Explainability	Share of flags where an officer can verify the evidence in under 2 minutes
Predictive value	Lead time and AUC for stall/overrun forecasts on a temporal holdout

4. Ideal Solution

A verification-prioritization system, not a fraud oracle:

Ingest and reconcile portal data with lineage.
Compliance engine. Every rule is traceable to a guideline clause (page or para) and a data field, with a confidence grade.
Statistical layer:
Peer-benchmarked unit-cost outliers (same normalized work type, district and year).
Duplicate-work candidates via blocking plus fuzzy matching.
Stall and overrun forecasting with survival or gradient-boosted models.
Evidence layer. Documents and photos add corroboration and never stand alone.
Prioritization. Rank by expected value at risk against verification cost.
Payment-time gate API that a District Authority or MoSPI system can call before a release.
Case management with a hash-chained log anchored externally.

AI/ML is warranted only in specific places: forecasting, unit-cost outliers, entity resolution, OCR, and LLM narration constrained to computed facts. Everything else should be rules and statistics.

Differentiators (ranked by impact ÷ effort):

Payment-time gate plus point-in-time replay backtest.
Title-normalized unit-cost benchmarking.
Human-labelled validation with precision@k and confidence intervals.
Stall/overrun survival forecast.
Duplicate-work detection (PS-explicit).
Evidence-tiered (not "crime"-labelled) alerts.
Rule provenance table (clause → rule → field).
Data-quality dashboard, so missing data is not mistaken for misconduct.
Officer workload simulator ("reviewing the top 500 catches X% more than random").
Notification and digest generation per role.

11. Security Audit
Unmasked PII via static mount [Doc]. The API masks bank accounts, but /images is mounted with StaticFiles. The rendered certificates contain the raw account numbers and UTRs. Anyone who can reach the path can read them. UNVERIFIED whether it sits behind auth. Serve images through an authorised endpoint and redact.
Password handling [Doc]. sha256(PASSWORD_SALT + password) uses a single global salt and a fast hash. Use argon2 or bcrypt with per-user salts. Demo users are hard-coded, which is fine for a prototype but must be disclosed.
SSE authentication [Inferred]. Browser EventSource cannot set an Authorization header. So the stream is either unauthenticated (open access to a paid Gemini endpoint) or the JWT travels in a query string. Check which. Add rate limits.
Role scoping coverage [Inferred]. apply_role_scope is described on DataFrames. Forensics JSON endpoints "serve the master payload directly", so they probably aren't scoped.
{work_id:path} route converters allow slashes. If a work ID ever reaches file access, that is a path-traversal risk. UNVERIFIED.
CORS is "enabled". Check that it isn't a wildcard.
Secrets: .env isn't in the root listing (good). Rotate anything ever committed. UNVERIFIED for history.
"DBAs cannot alter records" is false. A hash chain in a database the admin controls can be rebuilt end to end. It is tamper-evident only if the head hash is published or anchored externally. It is also a hash chain, not a "Merkle" structure.

13. AI/ML Audit
"5-model ensemble" is overstated. Only Model 1 (Isolation Forest) is a trained ML model. Model 2 uses embeddings for name matching. Models 3 and 4 are rules and heuristics, and Model 5 is the combiner. Model 4 is labelled "survival analysis" but is a threshold penalty with no survival estimator. Say "one anomaly model, one entity-resolution model, and a rule engine".
"Neural rendering" for PyMuPDF at 300 DPI is just rasterization. Drop the phrase.
Isolation Forest:
5% contamination flags 5% by design.
Features include the fabricated progress percentage.
There is no stability analysis (rank correlation under seeds and weight perturbation).
The overrun feature is dominated by the rule that already catches overspend.
Percentile-rank blending discards magnitude. A ₹500 crore anomaly and a ₹5,000 anomaly can receive the same rank.
Validation is circular.
92% corroboration: top-50 flags are checked against overspend, early payment and missing photo. Those are the same rules that force works into CRITICAL, so it is close to 100% by construction. It is not precision.
94% recall: you injected the anomalies, and your own rules are built to detect that pattern. It measures your test design, not real recall.
Retire both claims. Replace them with the validation plan in section 26.
LLM layer:
The memo "cites specific statutory clauses" including "Prevention of Corruption Act Section 13(1)(d)". As I recall, the 2018 amendment removed 13(1)(d). Verify it. If you cannot stand behind a clause, it must not appear.
Also check "GFR Rule 144", cited both for durable-asset prohibition and as the basis for show-cause notices. My recollection is that Rule 144 covers fundamental principles of public buying. Verify against the primary text.
LLMs should narrate computed facts only. Clauses should come from a curated lookup table, and a post-check should confirm every number in the memo exists in the input.
"Legally binding show-cause notice" overreaches. The tool drafts, and the District Authority decides.
Benford: Benford is weak on administratively set amounts (sanction estimates, round numbers, threshold-driven values). With n≈109k a chi-square test will always reject, and MAD is the right choice. I didn't see a reported MAD result in the docs. Frame Benford as a screening signal only.
Threshold "split-tender" rule: it flags any sanction in ₹4.5–4.99L or ₹9–9.99L, about 9% of works, without testing whether there is bunching relative to a smooth counterfactual density. Use a bunching estimator (excess mass with bootstrap CI), and add a check on adjacent works by the same agency and vendor in a short time window.
Threshold legal basis: you dropped state PWD thresholds and chose central GFR ones. MPLADS works are implemented by state and district agencies that usually follow state or CPWD works procedures. Check which rule actually binds, or hedge the claim.
